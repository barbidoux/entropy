benchmark session on the assembled game, at commit `68636eb` on `main`. Raw results:
`results/2026-11-20-183547-*.json`. Method: ADR 0007. The first session and the SPEC 3
recalibration are in `2026-11-20-m0-laptop.md`.

Differences from the first session:
- The memory clock stayed at 9001 MHz in every benchmark except the start of the house
  stencil, where it read 7001 MHz (P3) and was back at 9001 MHz by the end. In the
  first session it fell to 8001 MHz under the power cap.
- The enforced power limit varied from 110 to 122 W; it was a steady 110 W in the first
  session. This looks like the driver's dynamic boost moving power between CPU and GPU.
- The SM clock ranged from 1050 to 2310 MHz and the temperature from 82 to 93 °C,
  outside the first session's 1.3–1.7 GHz and 83–89 °C.

The sustained state therefore still depends on things M0 cannot pin down, and SPEC 3's
sustained-state line is widened to cover both sessions. The 450 GB/s planning figure
(the copy scaled to 8001 MHz) stays: the one 7001 MHz sample came at the start of a
benchmark. If the memory settled at 7001 MHz, the copy would scale to about 392 GB/s.
Telemetry sampled during each run (#25, M1) will show whether it does.

## Results against the first session

| Measurement | First session (16:31) | Gate session (18:35) |
| --- | --- | --- |
| Copy, `float` per thread | 503 GB/s | 503.5 GB/s (87 % of 576) |
| Read only, `vec4` | 560 GB/s | 560.4 GB/s (97 %) |
| Jacobi 128³, per sweep in a graph | 0.0282 ms (13.5 ps per cell) | 0.0319 ms (15.2 ps per cell) |
| Jacobi, house grid 160 × 128 × 96 | 0.0272 ms (13.8 ps) | 0.0294 ms (15.0 ps) |
| Jacobi 192³ | 0.199 ms (28.2 ps) | 0.185 ms (26.1 ps) |
| `wp.launch` from Python, host per kernel | 14.6 µs | 17.2 µs (p10–p90 15.9–19.5) |
| Graph of 100 kernels, host per kernel | 0.20 µs | 0.22 µs |
| Graph of 1,000 kernels, host per kernel | 0.69 µs (p90 1.10) | 0.47 µs (p90 0.93) |
| GPU time per kernel in graphs | 1.09–1.27 µs | 1.01–1.13 µs |
| Interop, 1 M particles (12 MB) per frame | trial only, not official | zero-copy 0.231 ms; host copy 6.70 ms (29×) |

- **Bandwidth** is reproducible to within 0.5 %. The read pass now reads a buffer of
  ones instead of zeros (a method change planned in the first report) and still gives
  560 GB/s, so compression of zero data did not flatter it.
- **Stencil:**
  - The L2-resident grids (128³, house) are 8–13 % slower than in the first session.
    The telemetry does not explain it: the house stencil ran at a higher SM and memory
    clock than in the first session and was still slower.
  - 192³ is 7 % faster with the memory at 9001 MHz instead of 8001.
  - The DRAM rate for planning stays at 28 ps per cell per sweep (26.1 ps measured
    here). The L2 rate spans 13.5–15.2 ps over the two sessions.
- **Launches:**
  - A plain launch from Python cost 18 % more than in the first session. Graphs of
    1,000 kernels got faster (0.69 to 0.47 µs per kernel; the p90 allows about 2,150
    kernels per 2 ms against 1,800 before). Graphs of 100 kernels went from 0.20 to
    0.22 µs per kernel.
  - SPEC 3's "about 1,800 graph kernels per frame" and "1.2 µs per executed kernel" stay
    conservative.
- **Interop:** zero-copy costs 1.4 % of a 60 fps frame (16.7 ms) for a million
  particles, 0.7 % of SPEC 3's 30 fps frame. The host copy (6.7 ms) would take 40 % and
  20 %. This is the first official measurement; the trial
  in #26 gave 0.2 ms against 6.1–8.9 ms.

The budgets hold, and SPEC 3 changes in two places:
- the sustained-state line is widened to cover both sessions;
- the optimistic ends of the estimates use each grid's slower L2 rate (house 15.0 ps
  instead of 13.8 ps, 128³ 15.2 ps instead of 13.5 ps).

| Estimate (optimistic end, per substep) | Was | Now |
| --- | --- | --- |
| House liquid solve, constant coefficients | 4.6 ms | 5.0 ms |
| House liquid solve, variational weights | 6.6 ms | 7.1 ms |
| Gas step, 96³ | 3.3 ms | 3.7 ms |
| Gas step, 128³ | 6.8 ms | 7.6 ms |

The planning ends (DRAM rate) are unchanged. The liquid at 2 substeps becomes
10–25 ms per frame instead of 9–25 ms.

## Soak test

`uv run pytest -m soak -s`, 600 s. The assembled game ran in a hidden window, with:
- random key presses (movement, up, down) and F3 toggles;
- mouse motion with the mouse captured;
- the 200,000-point interop pattern written by a Warp kernel every frame.

It ran on the laptop, plugged in, with the GPU otherwise idle, from 18:20 to 18:30.
The soak test does not record the power state: the benchmark harness read Best
performance on mains with energy saver off at 18:35, after its 5-minute warm-up, and
again around each benchmark. Its code was identical to `68636eb`; the branch differed
only in documentation.

| Measurement | Result | Limit |
| --- | --- | --- |
| Frames | 35,985 in 600 s, 60.0 fps (the 60 fps cap) | every frame completes |
| Process memory growth after the first minute | 0.0 MiB | < 64 MiB |
| Warp memory pool growth | 0.0 MiB | < 64 MiB |
| GPU-wide used memory growth | 0.0 MiB | < 64 MiB |

M0 has no solver yet, so this run proves the frame loop, rendering, interop and HUD are
stable, not the physics. The 30-minute soak with NaN checks is the M9 gate.
